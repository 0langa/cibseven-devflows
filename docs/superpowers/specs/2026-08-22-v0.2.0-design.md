# cibseven-devflows v0.2.0 — Design

Date: 2026-08-22
Status: Approved
Builds on: [v0.1.0 design](2026-08-22-cibseven-devflows-design.md)

## Why

v0.1.0 proved the shape: a release ritual as a BPMN process, external task workers, a human
approval, an MCP server. It works, and it released itself.

What it does not yet show is that a process engine is worth the trouble. Everything in v0.1.0
could, with effort, have been a shell script with a `read -p` in the middle. v0.2.0 adds the four
things that cannot:

1. **A decision that lives outside the code.** A DMN table decides whether a release needs a human
   at all. The rule is data, not an `if`.
2. **A step that asks an AI, with a human downstream.** Release notes are drafted by a local
   `claude` call and land in the approval form for a person to edit before anything is published.
3. **Failure handling that undoes work.** If publishing fails after the tag was created, BPMN
   compensation deletes the tag. A half-finished release leaves nothing behind.
4. **Waiting that ends.** A timer boundary event on the approval means a forgotten release rejects
   itself instead of sitting open forever.

Plus a robustness pass so the project reads as software rather than a demo.

## The v0.2.0 process

```
(start)
   │
   ▼
[run gates]                external task, devflows.gates
   │
   ▼
<gates passed?> ── no ─▶ (end: gates failed)
   │ yes
   ▼
[draft release notes]      external task, devflows.notes
   │
   ▼
[decide policy]            business rule task, DMN release-policy
   │
   ▼
<approval required?> ── no ──────────────────┐
   │ yes                                     │
   ▼                                         │
[Approve release]  ◀── timer ──▶ (end: approval expired)
   │                                         │
   ▼                                         │
<approved?> ── no ─▶ (end: rejected)         │
   │ yes                                     │
   ▼                                         │
[tag] ◀───────────────────────────────────────┘
   │  └─ compensation boundary ─▶ [undo tag]   devflows.untag
   ▼
[publish]                  external task, devflows.publish
   │  └─ error boundary (PUBLISH_FAILED) ─▶ (throw compensation) ─▶ (end: publish failed)
   ▼
(end: released)
```

### New and changed elements

| Element | Type | Notes |
| --- | --- | --- |
| `draft_notes` | External task, `devflows.notes` | Drafts release notes and classifies the release |
| `decide_policy` | Business rule task | `decisionRef=release-policy`, `mapDecisionResult=singleResult`, `resultVariable=policy` |
| `policy_gateway` | Exclusive gateway | Branches on `${policy.approval_required}` |
| `approval_timer` | Boundary timer on `approve_release` | `cancelActivity=true`, duration from `${approval_timeout}` |
| `end_approval_expired` | End event | Reached when the timer fires |
| `undo_tag` | External task, `devflows.untag` | `isForCompensation="true"`, never on the normal path |
| `compensate_tag` | Compensation boundary on `create_tag` | Wired to `undo_tag` by association |
| `publish_failed` | Error boundary on `publish_release` | `errorCode=PUBLISH_FAILED` |
| `throw_compensation` | Intermediate throw event | `compensateEventDefinition`, triggers `undo_tag` |
| `end_publish_failed` | End event | The release did not happen and the tag is gone |

## Technical failure versus business error

v0.1.0 had one failure mode: `POST /external-task/{id}/failure` with `retries=0`, which raises an
incident immediately. v0.2.0 separates two different things.

**Technical failure** — something that might work next time: the engine was briefly unreachable,
`gh` was not logged in, a command could not start. The worker calls `/failure` with a decreasing
retry count and a retry timeout, so the engine hands the task back after a delay. Only when the
retries run out does an incident appear. Schedule: 5 s, 15 s, 60 s, then incident.

**Business error** — something the process should decide about: publishing failed. The worker calls
`/bpmnError` with `errorCode=PUBLISH_FAILED`, the error boundary event catches it, and the process
compensates and ends. No incident, because nothing is broken; the release simply did not happen.

In the code this is `HandlerError` versus `BusinessError`.

## The decision table

`processes/release-policy.dmn`, decision id `release-policy`, hit policy FIRST.

| # | `release_kind` | `gates_passed` | → `approval_required` | `policy_reason` |
| --- | --- | --- | --- | --- |
| 1 | — | `false` | `true` | Gates failed, a human has to look |
| 2 | `"patch"` | `true` | `false` | Patch release with green gates, approved by policy |
| 3 | — | — | `true` | Minor or major release, a human decides |

`release_kind` comes from `draft_notes`, which compares the candidate version against the newest
existing tag in the repository. With no previous tag the kind is `major`, so a first release always
asks a human.

Rule 1 is unreachable in the current diagram, because the gates gateway ends the process first. It
is in the table anyway: the table states the whole policy, so it stays correct if the diagram
changes.

On the auto-approved path, `approved` is never set. That is deliberate — the variable means "a
human said yes", and no human did. The history records `approval_required=false` and
`policy_reason` instead.

## Release notes

`draft_notes` runs `git log <previous_tag>..HEAD --oneline` and feeds that, plus the gate report, to
a local `claude -p` call. Its output becomes `release_notes`.

- If `claude` is not on `PATH`, or the call fails or times out, the handler falls back to the raw
  commit list. `notes_source` records which happened: `"claude"` or `"git-log"`.
- Nothing is sent anywhere except to the local CLI the developer already runs. There is no API key
  in this project and no network call of its own.
- The notes are shown in the approval form as an editable field, so the human owns the final text.
  The value that comes back from the form is what gets published.

`publish.run` in `devflows.yaml` may use a `{notes_file}` placeholder. When it does, the handler
writes the approved notes to a temporary file and substitutes its path. This repository switches to
`gh release create v{version} --notes-file {notes_file}`.

## The approval timer

`approve_release` carries a boundary timer with `cancelActivity="true"`. Its duration is the
process variable `approval_timeout`, an ISO 8601 duration, defaulting to `PT24H`. `run gates`
echoes the default back when the variable was not set at start, so a run started with plain curl
still gets a timer.

Passing a short duration such as `PT2M` makes the timer demonstrable in a live demo.

## Robustness

- **Retries with backoff**, as described above.
- **`devflows-doctor`**, a third console script. It checks, in order: the engine answers; the
  `devflows-release` process is deployed; the DMN decision is deployed; a worker has polled
  recently; `devflows.yaml` in the current directory parses; `git` and `gh` are present and `gh` is
  authenticated. It prints one line per check and exits non-zero if any hard check fails.
- **Three more MCP tools**: `list_runs` (recent runs with state and version), `retry_run` (give
  failed external tasks another retry, clearing the incident), `cancel_run` (delete a running
  instance with a reason).
- **`get_run` reports incidents**, so a stuck run explains itself.

## Interfaces added

`devflows_core.versions`:

- `classify_release(previous: str | None, candidate: str) -> str` — `"major"`, `"minor"`,
  `"patch"` or `"unknown"`.

`devflows_core.engine.EngineClient`:

- `bpmn_error_external_task(task_id, worker_id, error_code, error_message, variables=None)`
- `list_incidents(process_instance_id=None) -> list[dict]`
- `set_external_task_retries(task_id, retries)`
- `delete_process_instance(process_instance_id, reason)`
- `list_historic_process_instances(key, limit) -> list[dict]`

`devflows_worker.handlers`:

- `NOTES_TOPIC = "devflows.notes"`, `UNTAG_TOPIC = "devflows.untag"`
- `class BusinessError(Exception)` with `code` and `message`
- `handle_notes(variables, *, runner=run_step) -> dict`
- `handle_untag(variables, *, runner=run_step) -> dict`

`devflows_mcp.tools`:

- `list_runs(client, limit=10)`, `retry_run(client, process_instance_id)`,
  `cancel_run(client, process_instance_id, reason)`, `doctor(client, repo_path=None)`

## What stays the same

The v0.1.0 contract does not move: process key `devflows-release`, the topics
`devflows.gates`, `devflows.tag` and `devflows.publish`, the start variables `repo_path`,
`version` and `dry_run`, the result variables `gates_passed`, `gates_report`, `approved`,
`approval_comment`, `tag_name` and `release_url`, and the seven original MCP tools. A v0.1.0 caller
still works.

## Testing

Every new unit is tested the same way as in v0.1.0: pure functions with an injected runner, engine
calls with `httpx.MockTransport`, MCP tools against a fake client. The BPMN and DMN files get
contract tests that assert the elements exist with the expected ids, topics and expressions.

New integration tests, all marked `integration`:

- A patch release with green gates auto-approves and never creates a user task.
- A minor release stops at the approval task.
- The approval timer fires and ends the instance when `approval_timeout` is short.
- A failing publish triggers compensation, and the tag is gone afterwards.
